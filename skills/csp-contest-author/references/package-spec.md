# 题包文件约定

在创建或修订文件前阅读。以下是默认交付格式，沿用 `2026-CSPJ-001` 的题目目录形式；用户指定的格式优先。

## 目录

```text
<contest-id>/
├── README.md                  整套题的定位、算法分布、运行方式、评分规则
├── make_data.py               从源码与种子重建全部正式数据
├── verify.py                  只检查，不更改 data/
├── validation-report.md       对当前文件实际运行后的验收记录
└── P1-<english-slug>/         单题保留 P1；整套继续 P2、P3、P4
    ├── statement.md
    ├── solution.md
    ├── src/
    │   ├── std.cpp
    │   ├── brute.cpp
    │   └── gen.cpp
    ├── data/
    │   ├── 1.in
    │   ├── 1.out
    │   └── ...
    └── work/
        ├── data_plan.json
        ├── make_data.py       本题的全量生成入口
        ├── validate.py        本题输入契约与子任务校验
        ├── stress.py          独立对拍及失败样例保存
        └── wrong_*.cpp        有针对性的错误/慢解；按实际需要创建
```

多题共用编译/运行逻辑时可放一个小型公共助手；不要重复复制大段脚本，也不必构建通用 OJ。由根目录脚本明确调用各题入口，不能靠遍历执行所有 `work/*.py` 来组织流程。备份和历史日志放 `archive/`，不参与当前测试点发现。

## 题面

用 `# 中文题名（slug）` 开头，明确时间、内存和输入输出方式。正文顺序通常为：题目描述、输入格式、输出格式、样例、数据范围与部分分。

样例采用现有项目格式，编号一一对应：

````markdown
## 样例输入 1

```text
3
1 2 3
```

## 样例输出 1

```text
6
```

## 样例解释 1

解释与本题规则相关的状态变化或方案，给出可手算的结果。
````

此处仅示范格式，不是待命制题目的内容。通常准备 2–4 组有不同目的的样例，不机械凑数。题面中的提示不能无意泄露目标算法。

数据范围必须覆盖全部输入字段；有测试组数时给出单组与全体规模上限。保证条件既写在题面，也由验证器逐点检验。`long long` 上界、空方案与不可达的输出必须能从模型推出。

## 题解

覆盖以下推理链，标题可随题调整：

1. 把题面对象映射到数学模型，明确什么需要保留为状态。
2. 朴素方案为何正确、在哪里超时或占用过多空间。
3. 关键观察、算法/状态/转移推导，避免“显然可以用某算法”跳步。
4. 可检验的正确性证明；贪心说明交换等依据，DP 说明完备性与边界，最短路说明状态和非负边前提。
5. 时间、空间和中间量上界；滚动数组按实际同时存活数组数估算内存。
6. 分值对应的部分解、与其复杂度匹配的数据限制，以及正解和各档部分解的必需前置与范围归类。
7. 指向 `src/std.cpp` 的相对链接，列明最容易犯的错误及反例。

如果题解内也展示完整代码，应检查与 `src/std.cpp` 同步，避免维护两个不同版本。来源/改编信息与命题者的算法意图写在教师可见部分。

## 可复现数据计划

`work/data_plan.json` 使用下列结构。此例只有两点，用于展示字段，并非推荐的正式数据数量：

```json
{
  "scoring": "sum",
  "subtasks": [
    {"id": "S1", "points": 50, "constraints": "n <= 10", "cases": [1]},
    {"id": "S2", "points": 50, "constraints": "完整范围", "cases": [2]}
  ],
  "solution_expectations": [
    {
      "source": "src/brute.cpp",
      "role": "slow",
      "guaranteed_subtasks": ["S1"],
      "score_range": [50, 50],
      "basis": "定义式枚举只在小规模可行，S2 检验最坏复杂度"
    }
  ],
  "cases": [
    {
      "id": 1,
      "points": 50,
      "seed": 1701,
      "args": ["min"],
      "purpose": "最小规模及起始状态",
      "tags": ["n-min"]
    },
    {
      "id": 2,
      "points": 50,
      "seed": 1702,
      "args": ["limit", "100000"],
      "purpose": "极限规模，检验朴素算法运算量",
      "tags": ["n-max", "complexity"]
    }
  ]
}
```

- `gen <seed> <args...>` 生成对应输入；每个点必须能仅依靠题包内容重建。
- `id` 为正整数，输入输出使用相同编号；每点恰属于一个子任务。更复杂的依赖式评分由用户要求驱动，届时扩展计划与检查器。
- `scoring="sum"`：各点独立得分，点分值相加为 100，组内各点之和等于子任务分值。
- `scoring="group-min"`：一个子任务的全部点通过才得到该组分值；各组分值相加为 100；点条目不填写 `points`。错解报告按此重新算分。
- `solution_expectations` 记录本题主要部分解和错解：`source` 为题包内程序路径，`role` 说明 slow/partial/wrong/correct 等用途，`guaranteed_subtasks` 引用保证全过的组（可为空），`score_range` 为 `[下界, 上界]`，满足 `0 <= 下界 <= 上界 <= 总分`，`basis` 解释依据。旧题包只在相关修订时补充，不为新字段批量改写历史包。
- 根目录 `verify.py`（可调用本题检查入口）负责检查代表程序、组引用及得分区间有效，按当前评分规则比较保证通过组和得分区间；`audit_package.py` 不解析或校验 `solution_expectations`。报告保留预期与实测两列及偏差处置，不能只输出通过点数。
- `constraints` 是说明文字，不能当作可执行校验；在 `validate.py` 中实现等价约束。
- `purpose` 写需要验证的具体行为；`tags` 是覆盖标签，脚本检查实际输入是否具备标签声称的性质，不只检查标签存在。
- 正式输入通常去重；若不同点刻意使用相同输入，后出现的条目须写 `duplicate_reason`，并评估是否浪费区分度。相同输出允许出现。

## 脚本运行约定

入口基于 `Path(__file__).resolve()` 定位题包，可以从任何工作目录运行；命令用参数列表传给 `subprocess`，避免拼接 shell 字符串。编译器优先取 `CXX`，否则探测 `g++`、`clang++` 或 `c++`；记录真实编译器版本、语言标准及优化选项。Windows 可执行文件后缀与其他平台区别处理。

生成器拒绝不合法/不可能的模式参数。固定种子并记录 RNG 实现；需要跨库逐字节复现时采用明确定义的随机数映射，而不是假定所有随机分布实现相同。

`make_data.py` 应先生成到临时位置，检查返回码、输入契约和输出，再发布。已有正式数据变化时保留可追溯备份；不得只更新 `.in` 而沿用旧 `.out`。生成失败不得打印成功。

`verify.py` 遇到任一必需检查失败，退出码非零并报告题号、点号/种子及原因；不在验证时覆盖答案。不用会被 `python -O` 禁用的 `assert` 作为输入合法性的唯一保障。对运行中的子进程设置适当超时；暴力只在其可行范围运行。

唯一输出用符合评测语义的 token 比对；不能为了方便强制所有题输出非负单整数。涉及多解、浮点或交互时，先调整 checker 和验收方式，再交付；不要套用逐字字符串比对。

## 验收报告内容

报告记录日期、当前源文件/正式数据的 SHA-256、环境与命令，以及：

- 每题定位、正解复杂度与部分解；正解及各档部分分的必需前置、范围依据与推导负担；样例/正式数据通过数。
- 独立校验方法、随机种子范围/实跑次数、适用规模；保存的回归反例。
- 各关键约束的实际覆盖证据，不只列最大值。
- 代表程序的保证通过组、预期得分区间、实际通过组/点、按真实评分规则计算的分数及失败原因；偏差的修复或接受依据与影响。
- 最大规模的实测时间与内存（只有测量过才填）；无法代表正式评测机时明确说明，不能保证跨机器时限。
- 重建两次的哈希是否一致；未验证项目及其影响。

`audit_package.py` 的通过结果只能放在“结构检查”一栏。不能据此代替上述运行证据。
