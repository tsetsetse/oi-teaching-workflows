# CSP-J/S 出题与验题

把出题要求落实为可编译、可复现、可检验的题目包。题面、算法、数据和评分共同构成一道题；标准程序输出了答案，只能证明生成过程完成，不能证明题目正确。

## 确定交付范围

先从用户要求与上下文提取：J/S、单题或整套、目标学生、已学/禁用知识、题号定位、原创或改编、指定算法、输出位置、时间/空间与评测约定。沿用已确认的选择。J/S 仍无法判断且影响命题时，只问这一关键项；一般实现细节自行决定。

未指定时采用以下工作默认值，并在首次进度说明中简短列出：

- 中文第二轮编程题；一套为四题，指定单题则只做一题。
- C++14、标准输入输出、确定且可直接比对的输出；这些是制作约定，不宣称是任何年份的官方规则。
- 每题 100 分、20 个测试点，默认每点 5 分独立计分；子任务按算法层次设计。用户指定打包计分时同步调整全部评分逻辑。
- 模拟赛由易到难，专题练习服从指定知识范围；不为了凑四题而强加高级算法。
- 新建不会覆盖已有内容的题包目录。修订已有题包时保留路径与用户内容，修改数据前备份被替换的输入和输出。

用户只要求构思/方案时，交付命题蓝图并止于该范围。用户要求完整出题时，在进度消息中说明蓝图后继续实现与验证；只有明确要求“先看方案再确认”时才等待确认。只要求修订时，不擅自另出一套题。

## 工作流程

### 1. 先确定可验证的模型

阅读 [quality-gates.md](references/quality-gates.md) 的难度与题意检查。为每题写出：一句话数学模型、核心约束、预期正解、独立暴力、复杂度、部分分算法、典型错误思路、难度依据。整套题记录在根目录 README，单题可写入题解的命题说明。

先推导算法和边界，再包装背景。若还不能证明算法，先解决模型；不要用生成大量随机数据掩盖证明缺口。改编题标注来源和实质变化；经典模型换故事应如实称为变式，不宣称已证明原创。

J/S 定位同时考虑知识前提、关键观察数量、证明难度和实现负担。为正解及每档部分分分别列出必需前置，区分“目标学生已学”“可由已学内容推导”“需要额外专门算法”。“已学完 CSP-J”允许使用完整入门级知识体系，不代表已学提高级算法；涉及层级不明的前置时核对官方资料与课程范围，记录链接和版本。超出范围则优先更换模型或解法；只有用户已要求或接受拓展时才作为拓展题采用，不能把它计入承诺的已学范围得分。严格对齐某年大纲/真题时核对对应年份；未核实的范围标明待确认。不要仅依据算法名称或数组维数判断难度。

### 2. 建立完整题目契约

按 [package-spec.md](references/package-spec.md) 创建题面与题解，保持当前任务指定的文件形式。题面需足以让另一位出题人独立实现相同规则，包括总规模限制、数字范围、操作顺序、空方案/无解、重复元素、端点是否包含等实际相关情况。

样例覆盖正常过程、关键边界和一种容易误读的规则。解释逐步核对输入与输出，避免仅重复答案。题解必须给出建模依据、朴素方案瓶颈、正解推导、正确性、复杂度、初始化/边界、整数上界及可实现的部分分。

### 3. 实现互相独立的程序

- `src/std.cpp`：与题解相同的完整正解，先运行手算样例和边界。
- `src/brute.cpp`：从定义枚举/搜索的小规模参考程序；不把正解改名或仅移除优化充当独立校验。写清可运行规模。
- `src/gen.cpp`：接收固定种子和模式参数，向标准输出生成输入。手工构造也做成生成模式，保证所有正式数据能从源文件重建。
- `work/validate.py`：独立检查输入格式、全局范围、子任务约束、结构性质和多组数据总量。校验不得按测试点编号跳过规则。
- `work/wrong_*.cpp`：实现与本题有关的典型错误/慢解，用于检验数据区分度；简单题可少写，复合约束题应覆盖各关键约束。区分答案错误、超时、崩溃与正确的替代算法。

默认使用标准库与已有编译器，无需引入评测服务或测试框架。编译产物放临时目录；使用当前机器编译的程序，不依赖随题包携带的旧 `.exe` 或作者电脑绝对路径。

### 4. 用设计目标生成数据

阅读 [quality-gates.md](references/quality-gates.md) 的数据与验收部分。先填写 `work/data_plan.json`，逐点记录种子、参数、子任务、分值、目的和覆盖标签，并按题包规范记录主要部分解、错解的保证通过组、预期得分区间与依据；再编写全量生成入口。预期在生成前确定，不能事后改成实测值来掩盖偏差。

每个决定复杂度或合法性的关键约束，都要有能区分“遵守”和“忽略”它的正式测试。覆盖适用的最小/最大、退化、零值、临界相等、顺序差异与不同参数组合；不能只用大随机和溢出点。只在答案确实可能越界时设计相应整数测试。

`make_data.py` 在临时目录生成并校验输入、计算输出，全部成功后再发布到 `data/`。小点用独立暴力确认，较大点使用第二实现、可证明的构造答案或变形关系补强。先确保标准程序可信，再批量产生答案。

### 5. 验证并交付

根目录 `verify.py` 应一键完成本题包实际需要的检查；生成和验证分为两个入口，验证不得自动修正答案或重生成输入来隐藏失败。

执行并记录：编译、样例、正式输入校验、全部 `.out` 复算、小规模随机/穷举对拍、关键边界、错解检验、极限规模运行，以及生成可重复性。检查项按风险与复杂度选取；随机数量是证据记录，不是正确性证明。编译、校验或对拍失败时保留日志、点号/种子与复现输入，停止发布并保留原正式数据；题面来源冲突未解决时也不得标记为可正式使用。修复后回归相关反例，再运行全量验收。

按实际评分规则对照预期与实测。保证通过组失分、得分超出区间或核心复杂度区分未兑现时，排查程序、数据覆盖和时限裕量，修正后重验；仅在不违反用户既定目标且报告写清接受依据与影响时保留偏差。不能只报告“慢解获得高分”就结束，也不能为匹配预期压制正确的高效替代算法。

对于默认目录格式，再运行：

```sh
python3 <本 Skill 路径>/scripts/audit_package.py <题包根目录>
```

该工具只检查文件、数据计划、评分和样例结构，输出 `LAYOUT_OK`；它不运行 C++，也不证明题目或标准答案正确。自定义格式应适配检查，不能为通过工具而改变用户要求。

在 `validation-report.md` 写清实际执行结果、环境、随机种子/次数、正式数据哈希、各代表程序的预期与实测得分、偏差及处置、耗时与未验证项。按最终数据重新生成报告，禁止复制历史日志当作新证据。没有编译器、重要独立验证未完成或既定得分目标未兑现时，交付已完成内容并准确标明待验范围，不标记为可正式使用。

最终向用户给出题包链接、每题知识点和难度依据、验证摘要及仍需判断的事项。若用户只需文件，保持回答简短。不要擅自发布到 OJ、覆盖原题库或向他人发送题目。
