## 1. 题解模式

根据题目复杂度合并标题，但保留推理顺序：

```markdown
# 题目名

## 题目契约
- 目标：
- 输入与范围：
- 输出与特殊情况：
- 操作和代价：

## 小样例手工模拟
（状态变化表或逐步过程）

## 计算思维分析
### 问题分解
### 抽象与建模
### 朴素解法与瓶颈
### 模式识别与优化

## 算法设计
（数据结构、顺序、更新、伪代码）

## 正确性说明
（不漏、不错、最优性）

## 复杂度分析
- 时间：
- 空间：

## 模型到代码
（变量映射 + 完整代码）

## 边界、反例与迁移
```

## 2. 讲义嵌入模式

不要在讲义末尾额外堆放一个与正文脱节的“计算思维”章节。把每一步放到学生真正需要作出判断的位置。

```markdown
### 第N段：从题面到模型（约 N 分钟）

> [!info] 教学场景
> （说明当前课堂任务）

#### 讲稿

（教师可直接说的话，先追问题意和规则，不先公布算法名）

> [!tip] 计算思维 · 问题分解
> （本题拆成哪些子问题，最难的是哪一项）

> [!question] 互动提问
> 问题：……
> 预期回答：……
> 追问：如果学生直接说算法名，要求补充哪项模型证据？

> [!tip] 计算思维 · 抽象与建模
> （对象、状态、操作、约束、不变量）

> [!bug] 经典误区
> 错误想法：……
> 最小反例：……
> 错因：……
> 修正：……

> [!important] 算法形成
> 朴素方案的瓶颈是……；观察到……；在满足……条件后，选择……。
```

板书至少保留这条主线：

```text
题目契约 → 小例子 → 状态/关系 → 暴力瓶颈
        → 结构证据 → 算法 → 正确性 → 复杂度
```

练习按梯度设计：

1. 模仿题：模型相同，只换情境或数据。
2. 变式题：改变一个守卫条件，判断原算法是否仍适用。
3. 综合题：需要组合两个模型或自行完成算法选择。

答案默认折叠：

````markdown
> [!example]- 参考答案（点击展开）
> ```cpp
> // 完整代码
> ```
````

只折叠练习答案；核心推导、关键代码和进阶主线保持展开。

## 3. 审查模式

按证据输出，不直接重写：

```markdown
## 审查结论
（一句话说明推理链是否完整）

## 必须修正
1. 位置或原句：
2. 问题类型：事实 / 契约 / 推理 / 复杂度 / 代码
3. 为什么影响理解或正确性：
4. 建议修改：

## 教学增强
（互动、板书、反例、梯度练习）

## 已经做得清楚的部分
（指出可保留结构，避免无必要重写）

## 建议实施范围
（明确哪些段落改，哪些保持不动，并等待授权）
```

“有四个标题”不等于计算思维完整。检查每个标题是否改变了后续推理：如果删掉该段，算法仍然凭空出现，这一段就是标签化说明。

## 4. 课堂互动设计

优先使用能暴露思维过程的问题：

- 你现在保留的状态信息，足够决定下一步吗？
- 哪两个输入会让这两种题意解释得到不同答案？
- 暴力算法重复做了哪件事？
- 如果把边权从 1 改成 0 或 2，原算法哪里失效？
- 被删除的候选为什么永远不会成为答案？
- 你能给这个贪心策略找一个反例吗？
- 代码里的 `dist[x][y][used]` 三个下标分别对应什么？

每个问题同时准备：预期回答、常见错误回答、教师追问。

## 5. Obsidian 约定

- 保持 YAML frontmatter 在文件最前方并闭合。
- 延续原笔记标题、wikilink、图片、平台链接和 callout 风格。
- Callout 每一行保持正确的 `>` 层级。
- 代码块标注 `cpp`、`python`、`plain` 或 `mermaid`。
- C++ 代码中的 `#include` 不转义。
- 标准代码给完整程序；平台专有函数明确标注运行环境。
- 若用户要求“先给建议”，在获得批准前不修改原笔记。
